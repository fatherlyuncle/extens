# Moxfield API Fixture Reference

Source: Moxfield responses captured in `test/moxfield/`.

The JSON fixtures are retained as raw responses. This document records the fields and structures present in those responses for use when developing the extension and its parsers.

# public-deck.json

## Root structure

The response contains detailed information for a public Moxfield deck, including deck metadata and keyed collections of cards.

The captured response contains normal deck-card entries such as:

```text
YMro6
Yle5e
YvQRq
kpP31
k7gOj
YnWGv
```

These keys correspond to Moxfield card/deck-entry identifiers.

There are also keyed card objects in the response that do not have the same complete deck-entry structure as the mainboard entries. For example:

```text
YoZ0V
ErngM
EPMq8
```

Therefore the parser should distinguish between:

1. deck-card entries containing quantity/board information and a nested `card` object; and
2. standalone card objects represented directly by their card fields.

## Deck-card entry

A normal deck-card entry contains:

```text
[entry].quantity
[entry].boardType
[entry].finish
[entry].isFoil
[entry].isAlter
[entry].isProxy
[entry].card
[entry].useCmcOverride
[entry].useManaCostOverride
[entry].useColorIdentityOverride
[entry].excludedFromColor
```

## Deck-specific fields

```text
[entry].quantity
[entry].boardType
[entry].finish
[entry].isFoil
[entry].isAlter
[entry].isProxy
```

The captured mainboard entries use:

```text
boardType = mainboard
```

but the parser should not assume that `mainboard` is the only possible value.

## Deck overrides

```text
[entry].useCmcOverride
[entry].useManaCostOverride
[entry].useColorIdentityOverride
[entry].excludedFromColor
```

These are Moxfield deck-specific values and should be preserved when normalizing deck data.

## Standalone card objects

The response also contains keyed card objects that have the card schema directly rather than being wrapped in a deck-entry object.

Example structure:

```text
[key].id
[key].uniqueCardId
[key].scryfall_id
[key].set
[key].set_name
[key].name
[key].cn
[key].layout
[key].cmc
[key].type
[key].type_line
[key].oracle_text
[key].mana_cost
[key].colors
[key].color_indicator
[key].color_identity
...
```

The captured response includes examples involving cards/tokens such as:

```text
Hangarback Assembler
Snake
Szat's Will
```

These should not automatically be interpreted as owned cards or deck cards merely because they occur in the response.

# decks.json

`decks.json` is a one-line JSON response in the captured fixture.

Its purpose is to provide the user's deck collection/listing rather than the full card contents of an individual deck.

The response should therefore be treated as the source for identifying decks and obtaining their associated metadata/identifiers.

The detailed contents of a selected deck are represented by the corresponding public-deck response.

The exact field inventory should be generated from the parsed JSON rather than inferred from the filename or from `public-deck.json`.

---

# Collection-specific data

The following fields describe the user's particular physical/digital copy rather than the underlying card:

```text
id
quantity
condition
game
finish
isFoil
isAlter
isProxy
purchasePrice
isPrefPrinting
createdAtUtc
lastUpdatedAtUtc
rarity
language
tradeBinder
```

These fields should not be conflated with the fields under `data[].card`, which describe the card/printing itself.

For example:

```text
data[].quantity
```

is the quantity owned in that collection entry.

By contrast:

```text
data[].card.name
```

is the name of the card represented by that entry.

---

# Deck-specific data

The following fields describe the card's role/printing in the deck:

```text
quantity
boardType
finish
isFoil
isAlter
isProxy
useCmcOverride
useManaCostOverride
useColorIdentityOverride
excludedFromColor
```

The nested `card` object describes the actual card/printing.

# Recommended normalized representation

The extension should eventually convert collection and deck responses into a common internal representation.

A normalized card record should be based on the data actually needed by the extension rather than reproducing the entire Moxfield object.

Suggested fields:

```text
name
scryfallId
moxfieldCardId
uniqueCardId

set
setName
collectorNumber

cmc
manaCost
type
typeLine
oracleText
colors
colorIdentity

power
toughness
loyalty

quantity

condition
game
finish
isFoil
isAlter
isProxy
isPrefPrinting

boardType

tradeBinder

useCmcOverride
useManaCostOverride
useColorIdentityOverride
excludedFromColor
```

The raw Moxfield object should remain available to the parser/test fixture even if only a subset of its fields is normalized.

# Important distinctions

`collection.json` answers:

```text
What cards does the user own?
How many copies?
Which printing?
Which condition?
Which finish?
Is it foil/altered/proxy?
Is it in a trade binder?
```

`decks.json` answers:

```text
What decks does the user have?
```

`public-deck.json` answers:

```text
What cards/objects are associated with a particular public deck?
How many copies?
Which board?
Which printing?
What Moxfield-specific deck overrides apply?
```

The card object embedded in these responses supplies:

```text
What card/printing is this?
What is its Scryfall ID?
What set/collector number?
What are its rules and characteristics?
What are its legality, price, and external-market data?
```

The extension should therefore treat:

```text
collection entry
```

and:

```text
deck entry
```

as different types of records that happen to contain a common underlying card object.

---

# Fixture handling

The files in this directory are raw captured Moxfield responses.

They should not be manually reduced to only the fields currently used by the extension.

When the extension needs additional Moxfield data, the existing fixtures should be inspected first to determine whether that data is already available.

If a required response structure is not represented by the existing fixtures, capture the corresponding Moxfield network response and add it as a new fixture.
